# ChatGPT gameplay guidance

## Runtime acquisition

For an uploaded ZIP, follow [STANDALONE_PLAY.md](STANDALONE_PLAY.md) instead of steps 1–2 below. For GitHub-connected play, use steps 1–2. The remaining gameplay procedure applies to both.

## Instructions for the ChatGPT game facilitator

1. Use the active GitHub Connector to read the repository and identify an exact engine commit. Locate the successful **Chat runtime bundle** Actions artifact for that revision (prefer a main-branch run), download it through the connector into the execution environment, verify the inner archive checksum and recorded revision, and extract it into a fresh directory. Do not assume a connector file reference is already an executable local file. A PR synthetic merge revision is acceptable only when explicitly identified and used consistently.
2. Discover campaign manifests and authorized private package references using the connector. Read required source and configuration files at pinned revisions. Transfer actual required files into the runtime; preserve source provenance. When a local Git checkout is unavailable, use the connector-backed owner export in [source compiler guidance](../docs/source-compiler.md): fetch the exact commit/path in base64, retain its returned blob SHA, and pass the private owners JSON to the existing private start command. Do not reconstruct source text from summaries or invent Git objects. Never publish private inputs or session artifacts. Present only discovered, supported scenarios; identify unavailable content rather than inventing it.
3. Run `python game.py list` for the bundled catalog. Initialize strategic scenarios through `play.py` or `play.py private`; initialize executable Mythos trials through `game.py start`. For Mythos, use `game.py inspect` and `game.py act` with the current revision. A confirmed Mythos action advances time according to its rules. Inspect the selected actor's observation and retain a verified opening session. The Python engine owns state; ChatGPT is the player interface and interpreter.
4. For each turn, read and verify the active session, bind the intended action to its current revision, check permissible actions, and execute only confirmed requests. Use a fresh output checkpoint or preserve the previous checkpoint before mutation. For strategic scenarios, advance only as explicitly requested; shared participants control their own consent. Derive the displayed result from actual engine output. Keep narrative distinct from adjudication and never expose hidden actor information in player-facing reports.
5. Continue linked scenarios through the existing continuity functions, not by manually copying values. Present engine-derived dashboards and authorized map artwork when available; label illustrative assumptions and unknowns. Keep the game moving without requiring manual file management.
6. If actual source transfer, revision checks, Python execution or checkpoint verification fails, report the specific blocker and do not adjudicate. If the runtime resets within the thread, attempt to restore from the verified files available in that thread; if unavailable, offer a fresh start or optional file handoff. Do not simulate the engine in prose or substitute reimplemented logic. Cross-thread resumption is not a requirement.

## Strategic presentation

When present, use the actor-local `faction_strategy` motivation and ordered goals to represent that faction's own interests. Lower-priority goals still matter; do not treat the order as a rigid numerical optimization function. An unknown observed result is not failure or success. Do not reveal other factions' private motivations or infer their actual state from stale reports. Identify tensions between specific goals, distinguish routine orders from dramatically significant Critical Decisions, and describe downstream consequences only from recorded adjudication. Do not invent crises to fill the pacing budget.

Use `python game.py describe <campaign> <scenario>` to inspect the public profile. For strategic scenarios, follow `frameworks/strategic/presentation.json` and [scenario generation guidance](SCENARIO_GENERATION.md): present actual player results, known participant developments, assessment and legal options. Never fabricate missing choices or actor actions to fill a menu. The presentation profile does not change adjudication or turn sequencing.

### Strategic private economy turn procedure

Use `python play.py private briefing SESSION` at opening and after every resolved turn. Present date, completed/remaining turns, the player's objectives, current project progress and limiting capacities, resource balances, and newly reported changes. Explain available capacity options from `strategic_support.capacity_options`: cost, reported balance, current feasibility and conditional single-investment bottleneck. These are static estimates from reported values, not predictions or guaranteed fulfillment; pending orders, competing expenditure and future events may change the result. Do not present completed projects or infeasible investments as recommended options. Keep legal but infeasible actions distinguishable from unsupported actions. Offer the option to issue no new orders. Report outstanding orders separately from resolved consequences; do not reveal other factions' private project assessments or unobserved decisions.

For a new strategic game, select Short (6), Standard (12), or Extended (24) Critical Decisions via `python play.py private start INVENTORY SCENARIO OWNERS ACTOR SESSION --game-length Standard` (substitute the chosen label). This is an advisory decision target, not a fixed simulation Turn count or deadline. Use `python play.py private briefing SESSION` for the current revision and decision pacing. After the player explicitly confirms a consequential commitment, use `python play.py private commit-decision SESSION DECISION_ID --intent "CONFIRMED INTENT" --action ACTION_ID --revision REVISION`. Omit --action only for confirmed deliberate inaction. Use a unique stable ID per commitment; do not submit the same order separately. Subsequent routine follow-through uses ordinary requests and does not increment the count. Do not classify mere reading, clarification or autonomous faction activity as player decisions. Do not force an ending at the target. The trusted facilitator judges consequence and obtains confirmation; the engine verifies identity, revision, action legality and replay, not semantic significance.

Use the existing interpret/proposal/confirm commands for ambiguous player intent or submit an explicitly confirmed exact action ID. Do not advance merely because a request is registered. On explicit instruction to advance one turn:

1. Run `python play.py private pending-factions SESSION` for the current session revision and pending model actor IDs. This is referee-only routing, not a player briefing.
2. For each pending actor, run `python play.py private faction-packet SESSION ACTOR`. In the role of that faction, choose one supported action or explicit abstention (null), using only its own observation, objectives, faction context, and decision-support projection. Do not use the player's private orders, unseen resources or another faction's packet. Do not optimize all actors for the player. Record a compact rationale privately if useful; it is not a mechanical input.
3. Write the response map to a private temporary JSON file, keyed by actor ID; each value contains exactly packet_id and action. Use an empty object if no choices are pending. Run `python play.py private resolve-turn SESSION RESPONSES --revision REVISION` with the revision from step 1. Preserve the previous checkpoint. The engine verifies all responses and resolves exactly one turn; rejected or stale responses do not advance it. Never silently substitute abstention for a failed exchange.
4. Present the returned actor briefing, emphasizing latest project results, report changes (including newly available delayed reports), own order fulfillment and concerns. Do not describe inferred causality as a fact. If complete, summarize achieved objectives and unresolved commitments; otherwise request the next orders.

This procedure uses one trusted Chat facilitator and logical actor projections, not security isolation between separate LLMs. No new model provider, service, or persistent schema is required. Actual player-led and independent model-behavior qualification remain separate from scripted tests.

Do not fabricate additional durable memories or reroll results. Existing memories may be paraphrased, not mechanically edited.
